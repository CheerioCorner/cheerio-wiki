Plannotator × Obsidian

把一次 AI 討論，變成可審查、可累積、可分享的工作成果

2026-08

大家是不是也遇到這些問題？

這些是我個人在使用 AI 時遇到的困境，想跟大家確認：這些問題是不是也是你們的痛？

1

AI 產出的結果，常常不是我要的

有時候和 AI 討論東西，它出來的規劃有多處我不是很認同，或者我覺得還可以再調整。

但往往很難一次性地全部表達，讓 AI 一次統整性地去思考。

💡 這就是為什麼 Plannotator 對我有幫助 — 它讓我能一次把所有反饋整理好，送回給 AI。

2

讀了很多資料，但它們散落各處

過往常常讀到很多資料，它們之間都是有關聯的，但資料總是被散落各處。

我需要一個工具，幫我把資料之間的關聯整理出來。

💡 這就是為什麼 Obsidian 對我有幫助 — 它可以讓 AI 來整理關聯，而我只需要 Human in the loop。

我想要表達的是：我想以個人遇到的問題，讓大家延伸想想——這是不是也是你們遇到的問題？
如果是，我們怎麼解決？

知識迴流：從輸入到沉澱

不限來源的資訊，透過 AI 整理後沉澱到知識庫；當有問題時，再從知識庫出發，結合 AI 研究，產出成果。

🧩 先搞懂一個詞：Loop Engineering

最近很紅的詞，用白話解釋就是：在讓 AI 做事之前，先讓它說清楚「它打算怎麼做」。

🔥 為什麼最近很紅？

因為大家發現：直接叫 AI 「幫我做 XXX」，結果往往不滿意。

不是 AI 不行，而是我們沒有把需求講清楚。

Loop Engineering 的核心：AI 不是一次回答完，而是透過問題 → 工具 → 證據 → 回饋，逐步收斂到我們要的結果。

💡 為什麼 Plannotator 在此時很關鍵？

當 AI 說「我打算這樣做」的時候，它需要一個人類的 Review Gate：

  • ✓ 你說清楚了嗎？
  • ✓ 你的假設對嗎？
  • ✓ 你有漏掉什麼嗎？
  • ✓ 你的範圍對嗎？

Plannotator 就是那個 Review Gate — 讓人類在 AI 執行前，先審查它的計畫。

一句話總結：AI 不是一次回答完，而是透過問題、工具、證據與回饋逐步收斂。Plannotator 是讓這個收斂過程可視化、可審查的關鍵工具。

現在，讓我們實際操作

接下來示範：從「提出問題」到「AI 產出 Plan」到「Plannotator 審查」到「存入 Obsidian」的完整流程。

📐 Plannotator：AI 工作的 Review Gate

不只是 coding tool — 所有 AI 產出（Plan、Code、Markdown、HTML、URL）都可以納入審查。

🔄 Review Gate 流程

🤖
AI 產生 Plan
研究範圍、假設、證據
→
📐
Plannotator Review
瀏覽器標註 UI
→
✅
核准 / 駁回
含批註回饋

批註範例：「範圍太大」、「缺少公司內部標準」、「請補充成本評估」、「需要說明維運責任」

Plannotator 把 AI 的計畫、程式碼、文件與網頁內容，放進同一個人類審查流程。

以下檔案類型都可以用 Plannotator 審查：

功能 指令 說明
Plan Review Shift+Tab 進入 Plan Mode 檢查研究範圍、假設、證據、評估維度與報告格式；核准或駁回。
Code Review /plannotator-review 審查未提交的程式碼變更，或貼 PR 網址審查，對錯誤加行級留言。
Markdown / HTML 標註 /plannotator-annotate <檔案路徑> 對研究報告、架構圖或 HTML 預覽逐段加註。
標註最後一則回覆 /plannotator-last 對 AI 剛剛給的回答直接加註，不用先另存成檔案。
💡 過去經驗：使用 Plannotator 後，溝通次數大幅減少。以往需要 10 次以上的溝通，通常 1 到 2 次就結束。即使太過複雜的問題可能還是會比較多輪，但還是比沒有使用之前好很多。

🔗 Plannotator × Obsidian：無縫整合

Review Gate 與知識庫之間真正的橋樑 — 不用手動搬運檔案。

⚙️ Plannotator 內建 Obsidian Integration

設定方式：

Settings → Obsidian Obsidian Integration: ON Vault: C:\CheerSpace\90_Wiki Folder: raw/plannotator

自動產生的 Frontmatter：

created: 2026-08-21T10:00:00Z source: plannotator tags: [plan, ...]

實際操作流程：

  • 1. 在 Plannotator 中核准計畫
  • 2. Options → Save to Obsidian
  • 3. 檔案直接出現在 raw/plannotator/*.md
  • 4. 帶著 frontmatter，銜接下一步的 wiki 整理

✓ 0 手動搬運

這是知識閉環迴流的關鍵接合點：Plannotator 審查完畢 → 一鍵存入 Obsidian → AI 整理到 Wiki → 未來的研究可以從 Wiki 出發。

🧠 Obsidian：第二大腦與 Knowledge Graph

為什麼是「第二大腦」？這個概念源自 Andrej Karpathy 提出的 LLM Wiki 想法，以及 Google 的 OKF（Open Knowledge Foundation）精神。 我們結合了這些概念，用 Obsidian 實作。

📊 資料流

📥
raw/
原始資料（唯讀）
→
🤖
wiki ingest
整理、萃取、建立連結
→
📚
wiki/
sources / concepts / entities

Obsidian 只是 Wiki 的閱讀、瀏覽與關聯探索介面；Markdown 才是可長期保存、可被 AI 讀寫的知識格式。

🔍 Graph View 的四個價值

不是炫技的圖，而是系統性治理判斷工具：

🔗 發現關聯

節點間的連線，顯示概念如何互相支撐。

🕳️ 知識缺口

應該存在卻缺少的連結。

⭕ 孤兒頁

沒有任何連結的獨立節點。

🏛️ 決策樞紐

連結數量最多的核心節點。

📤 從同一份知識，輸出多種成果

當你把這套用好，從同一份研究內容可以輸出多種不同的成果，達到徹底的知識迴流。

🏢 核心概念

Obsidian Wiki 是知識整理與維護的作業工廠；PPT 與 Azure DevOps Server Wiki 是面向不同受眾的成品與協作介面。

📊 PPT

對象：主管與分享會聽眾

用途：快速掌握背景、問題、方案、風險與建議；適合簡報、決策會議與跨單位溝通。

📖 Wiki

對象：ITD 團隊

用途：可搜尋、持續更新、補充留言與連結；成為後續需求、架構與維運工作的知識基礎。

📁 其他

對象：視需求而定

用途：Dapps、SharePoint、個人報告（Word / PDF）。

🚀 安裝與落地

方法一（推薦）— 讓 AI 自己動手裝

npx skills@latest add \ https://github.com/EVACopilot/skills-itd-aas \ --skill plannotator-copilot-setup

然後在 AI 對話框輸入：

/plannotator-copilot-setup

AI 會自動完成「安裝執行檔＋停用分享」，並回報「接下來要手動做的事」清單。

接下來 3 件事仍要手動做

  • 1. 安裝 Copilot 外掛：貼上兩行指令，或到 Settings → Plugins 搜尋 plannotator
  • 2. 完整重新啟動 GitHub Copilot App（不是只開新分頁），PATH 與外掛才生效
  • 3. Shift+Tab 進入 Plan Mode，驗證是否自動跳出 Plannotator 審查頁面

🔒 隱私與資安

  • 核心 Plan / Code / Annotation 全程在 localhost 執行，官方政策不蒐集使用行為
  • Ask AI / 自動程式碼審查會直接送到機器上已登入的 AI CLI（不經 Plannotator 伺服器）
  • 公司政策只核准 Copilot 時，不要額外安裝並登入 claude / codex / pi / opencode 等個人帳號

這是我個人摸索出來的工作方式。
工具可以用別的，流程可以不一樣。
重要的是：找到適合你自己的方式。

我不做保證，但我相信：
每個人的工作方式不同，每個人的學習路徑也不同。這套工具和流程對我有幫助，但不代表它對每個人都是最佳解。

我能做的是：把我知道的分享出來，讓大家有機會去嘗試、去摸索，
